# DM-System — оновлення GraphQL + MongoDB

Це набір файлів для інтеграції реальної авторизації, реєстрації компанії, приєднання за запрошенням і роботи вебробочого простору з MongoDB через єдиний GraphQL API.

## Що реалізовано

- Реєстрація з двома сценаріями: створити компанію (роль `ADMIN`) або приєднатися за кодом запрошення (роль `DROPSHIPPER`).
- Вхід за email і паролем, хешування паролів через bcrypt, JWT-токен із серверною перевіркою користувача.
- Перевірка ролей на сервері. Frontend більше не дозволяє перемикати роль вручну.
- Ізоляція даних за `companyId`, який береться з авторизованого користувача, а не з аргументів клієнта.
- MongoDB-моделі `Company`, `User`, `Invitation`, `Product`, `Order`; позиції замовлення зберігаються як вкладені `OrderItem`.
- Одноразові запрошення з терміном дії, хешуванням коду та можливістю відкликання.
- Каталог: створення, редагування, видалення, пошук і фільтрація. Керувати каталогом може адміністратор.
- Замовлення: дропшипер створює замовлення з кількома товарами; сервер перевіряє залишки й списує їх; адміністратор керує статусами та бачить замовлення компанії.
- При скасуванні замовлення зарезервований залишок повертається. Після завершення замовлення він не повертається при видаленні запису.
- Адміністратор може переглядати користувачів, створювати/відкликати запрошення та деактивувати/активувати учасників.
- Налаштування назви компанії.
- Web UI підключений до GraphQL через Apollo Client; демонстраційні `localStorage`-дані більше не є джерелом даних робочого простору.

## Структура оновлення

- `server-graphql/` — замінити відповідні файли в наявній теці сервера та додати нові підтеки `config`, `models`, `utils`.
- `app/` — замінити відповідні файли у вебзастосунку та додати Apollo Client, Auth Context, сторінку входу/реєстрації й екран компанії.

Існуючі публічні компоненти головної сторінки, стилі робочого простору, таблиці, картки та утиліти залишаються на місці. Файли в архіві мають ті самі відносні шляхи, тому їх можна скопіювати поверх кореня репозиторію.

## Налаштування та запуск

### 1. MongoDB

Потрібен локальний MongoDB або MongoDB Atlas. Для локального сервера типовий URI:

```env
MONGODB_URI=mongodb://127.0.0.1:27017/dm-system
```

Для Atlas використай URI свого кластера й дозволь мережеве підключення з IP, з якого запускається API.

### 2. GraphQL API

```bash
cd server-graphql
```

Скопіюй `.env.example` у `.env` і задай власні значення:

```env
PORT=4001
MONGODB_URI=mongodb://127.0.0.1:27017/dm-system
JWT_SECRET=ЗГЕНЕРУЙ_ВИПАДКОВИЙ_СЕКРЕТ_МІНІМУМ_32_СИМВОЛИ
CLIENT_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
JWT_EXPIRES_IN=1d
```

Потім:

```bash
npm install
npm run dev
```

API буде доступний за адресою `http://localhost:4001/`.

### 3. Web frontend

В іншому терміналі:

```bash
cd app
```

Скопіюй `.env.example` у `.env`:

```env
VITE_GRAPHQL_URL=http://localhost:4001/
```

Потім:

```bash
npm install
npm run dev
```

Відкрий адресу Vite, зазвичай `http://localhost:5173/`.

### 4. Перший запуск

1. Відкрий `/register`.
2. Обери «Створити власну компанію».
3. Заповни ім'я, email, пароль і назву компанії. Цей користувач автоматично отримає `ADMIN`.
4. У робочому просторі відкрий «Користувачі» та створи запрошення.
5. Передай код іншій людині.
6. Вона відкриває `/register`, обирає «Приєднатися до компанії», вводить код і створює свій обліковий запис `DROPSHIPPER`.

Код запрошення показується лише один раз після створення. Якщо його втрачено, створи новий і відклич старий.

## Важливі правила безпеки

- Не додавай `.env` до Git. У репозиторій додаються лише `.env.example`.
- Не використовуй секрет із прикладу як production-секрет.
- Усі перевірки ролі та належності до компанії виконуються на сервері.
- У цій версії токен зберігається у `localStorage` для простого SPA/Bearer-сценарію. Для production варто перейти на secure, HttpOnly cookies або іншу захищену схему з урахуванням мобільного клієнта.
- Email-повідомлення не надсилаються: код запрошення передається адміністратором вручну. Інтеграція поштового сервісу не входила до зафіксованих вимог.
- Для production потрібно додати rate limiting, підтвердження email, процес відновлення пароля, журнал аудиту та HTTPS.

## Перевірка після встановлення

1. Створення компанії створює рівно одного першого адміністратора.
2. Повторна реєстрація з тим самим email відхиляється.
3. Неправильний пароль не дозволяє увійти.
4. Неправильний, використаний, прострочений або відкликаний код запрошення не дозволяє приєднатися.
5. Приєднаний користувач отримує тільки роль `DROPSHIPPER`.
6. Дропшипер не може створювати/редагувати/видаляти товари, переглядати інших користувачів або змінювати статуси замовлень.
7. Дропшипер бачить тільки власні замовлення.
8. Користувач однієї компанії не може прочитати або змінити дані іншої компанії.
9. Створення замовлення зменшує залишок; скасування повертає зарезервований залишок; завершення не повертає його.
10. Після перезапуску API дані залишаються в MongoDB.

## Межі цієї поставки

Це інтегрований вебклієнт і GraphQL backend для зафіксованих основних сценаріїв DM-System. Мобільний клієнт React Native ще не входить до цього архіву: він зможе використовувати той самий API, токен і модель ролей без створення другої системи даних.


## Лабораторна робота № 7–8: спільне ядро та monorepo

У корені репозиторію налаштовано npm workspaces:
- `app/packages/core` — платформонезалежні правила DM-System: валідація товарів і замовлень, переходи статусів, фільтрація та форматування;
- `app` — React/Vite Web-клієнт;
- `app/desktop` — Electron-клієнт і файловий адаптер для локальних налаштувань.

Web та Electron використовують один `createStorageService()` із Core через платформні адаптери. Бізнес-дані каталогу, замовлень і користувачів залишаються на GraphQL/MongoDB; локальні адаптери зберігають налаштування робочого простору, щоб не створювати другу, неузгоджену копію серверних даних.

### Встановлення та перевірки

З кореня репозиторію:
```bash
npm install
npm test
npm run build:web
```

Окремі тести:
```bash
npm run test:core
npm run test:web
npm run test:desktop
```

Запуск:
```bash
npm run start:web
npm run start:desktop
```

GraphQL API запускається окремо:
```bash
cd server-graphql
npm install
npm run dev
```

### Платформна архітектура

- Core не імпортує `window`, `localStorage`, `document` чи Electron.
- Web адаптер використовує `localStorage`.
- Electron адаптер викликає лише дозволені методи preload bridge; файловий доступ реалізовано в main process.
- Electron renderer працює з `contextIsolation: true`, `nodeIntegration: false` і sandbox.

## Технологічний стек і компетентності

DM-System розробляється як кросплатформний застосунок із веб-, мобільним і десктопним клієнтами. Для кожної платформи використано відповідні інструменти, а спільні частини винесено в окремий пакет.

### Технологічний стек

| Рівень | Технології | Реалізація в проєкті |
|---|---|---|
| Платформи | Web, Mobile, Desktop | Окремі клієнтські середовища для роботи із системою |
| Web-клієнт | React, Vite, React Router, Styled Components, Apollo Client | Інтерфейс у теці [app](app/) |
| Mobile-клієнт | React Native, Expo | Мобільний застосунок у теці [mobile](mobile/) |
| Desktop-клієнт | Electron, Vite | Десктопна оболонка у теці [app/desktop](app/desktop/) |
| Спільний код | JavaScript, npm workspaces, @dm-system/core | Пакет [app/packages/core](app/packages/core/) |
| Платформні адаптери | LocalStorage, Electron preload bridge, IPC, File Storage | [Web-адаптери](app/src/adapters/), [Desktop-адаптери](app/desktop/) |
| GraphQL API | Node.js, Apollo Server, GraphQL, JWT | Сервер у теці [server-graphql](server-graphql/) |
| REST API | Node.js, Express | Окремий сервер у теці [server](server/) |
| База даних | MongoDB, Mongoose | Підключення та моделі серверної частини |
| Інструменти | Git, GitHub, npm, dotenv | Контроль версій, залежності та конфігурація середовища |

### Архітектура та взаємодія компонентів

```mermaid
flowchart TB
  subgraph Platforms["Платформи"]
    W["Web"]
    M["Mobile"]
    D["Desktop"]
  end

  subgraph Clients["Клієнтські технології"]
    WC["React + Vite + Apollo Client"]
    MC["React Native + Expo"]
    DC["Electron + Web UI"]
  end

  subgraph Shared["Спільний код та адаптери"]
    CORE["@dm-system/core"]
    WA["LocalStorage Adapter"]
    DA["Desktop Adapter"]
    IPC["Preload Bridge / IPC"]
    FS["File Storage Adapter"]
  end

  subgraph Backend["Серверний рівень"]
    G["Apollo Server / GraphQL / JWT"]
    R["Express REST API"]
  end

  DB[("MongoDB")]

  W --> WC
  M --> MC
  D --> DC
  WC --> CORE
  CORE --> WA
  CORE --> DA --> IPC --> FS
  WC --> G

  G --> DB

```

Спільний пакет `@dm-system/core` надає сервіс зберігання з методами `get`, `set` і `remove`. У Web використовується LocalStorage Adapter. У Desktop операції передаються через preload bridge та IPC до файлового адаптера. Мобільний клієнт має окрему реалізацію зберігання токена; його використання пакета `@dm-system/core` не підтверджене.

GraphQL API є основним API для вебклієнта. Окремий Express REST API також присутній у репозиторії, але його використання основними клієнтами не підтверджене.

### Основні архітектурні рішення

- React використано для побудови компонентного вебінтерфейсу, React Native та Expo — для мобільного клієнта.
- Electron дає змогу запускати вебінтерфейс у десктопному середовищі та працювати з файловим сховищем через IPC.
- GraphQL та Apollo Server забезпечують взаємодію вебклієнта із серверною частиною.
- MongoDB та Mongoose використовуються для зберігання серверних даних.
- Адаптери ізолюють платформні відмінності локального зберігання: спільний сервіс працює з однаковим набором методів, а реалізація залежить від платформи.

### Основний кросплатформний виклик

Однією з відмінностей між платформами є спосіб локального зберігання. Браузер використовує `localStorage`, тоді як Electron працює з файловою системою через main process та IPC. Для цього створено спільний інтерфейс сховища й окремі адаптери. Завдяки цьому код, який використовує методи `get`, `set` і `remove`, не повинен знати деталі конкретного сховища.

### Набуті компетентності

Під час розробки DM-System були опрацьовані такі навички:

- створення SPA на React та організація компонентної структури;
- розробка мобільного клієнта на React Native та Expo;
- створення десктопної оболонки на Electron;
- побудова REST API та GraphQL API на Node.js;
- використання MongoDB і Mongoose для роботи з даними;
- реалізація JWT-авторизації;
- застосування адаптерів і відокремлення платформозалежного коду від спільного сервісу;
- робота з npm workspaces, Git і GitHub.

### Приклади реалізації в коді

1. **Спільний сервіс зберігання:** `app/packages/core/src/services/storageService.js`.
2. **Вибір адаптера залежно від середовища:** `app/src/lib/platformStorage.js`.
3. **Безпечний міст Electron:** `app/desktop/preload.cjs` та `app/desktop/ipcHandlers.js`.
4. **GraphQL сервер:** `server-graphql/index.js`, схема та резолвери в теці `server-graphql`.

## Запуск платформ

Перед запуском переконайтеся, що налаштовані `server-graphql/.env` та `mobile/.env` на основі відповідних `.env.example` файлів. Не додавайте `.env` до Git або публічних архівів.

- GraphQL API: з кореня репозиторію `npm run start:api` (або `npm run dev` у `server-graphql`).
- Web: `npm run start:web`.
- Desktop: `npm run start:desktop`.
- Mobile / Expo: `npm run start:mobile`.

Для Web на тому самому комп'ютері Mobile може використовувати `http://localhost:4001/`. Для фізичного телефона в `mobile/.env` вкажіть LAN IPv4-адресу комп'ютера, наприклад `EXPO_PUBLIC_GRAPHQL_URL=http://192.168.1.25:4001/`. Телефон і комп'ютер мають бути в одній мережі. Після зміни `.env` перезапустіть Expo з `npx expo start -c`.
